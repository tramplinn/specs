# Проекты пользователей

Статус: черновик · Дата: 2026-10-03

## 1. Зачем

Пользователи хотят показывать, что они делают, а не только что прошли: учебные и
пет-проекты, командные работы, хакатоны. Проект — это карточка с README в Markdown,
логотипом, ссылками (репозиторий, демо, документация), командой с ролями и статусом.
Проекты отображаются в публичном профиле (`/people/:login`) всех участников, а
пользователь сам решает, какие блоки профиля показывать и в каком порядке.

## 2. Объём

Входит:

- создание, редактирование, архивация и удаление проекта;
- README в Markdown, краткое описание, логотип;
- ссылки на репозитории и прочие ресурсы;
- участники: приглашения, роли, выход и исключение, передача владения;
- статусы проекта и история их смены;
- видимость проекта;
- блок «Проекты» в профиле и настройка видимости и порядка блоков профиля.

Не входит (кандидаты на следующие итерации):

- хранение артефактов (файлов) проекта;
- интеграция с GitHub/GitLab API (звёзды, коммиты, языки);
- привязка проекта к курсу (финальный проект);
- комментарии, лайки, подписки на проект;
- канбан с drag-and-drop по статусам;
- инструменты для проектов в `mcp-server`;
- модерация (скрытие) публичных проектов админами и лимиты на число проектов.

## 3. Термины

| Термин | Значение |
|---|---|
| Проект | Сущность `Project`, идентифицируется `slug` в URL |
| Участник | Пользователь с записью в `project_members` |
| Владелец | Единственный участник с ролью `owner` |
| Приглашение | Запись `project_invites` в статусе `pending` |
| Блок профиля | Секция публичного профиля: «О себе», «Статистика», «Курсы», «Резюме», «Проекты» |

## 4. Модель предметной области

### 4.1. Статусы проекта — `ProjectStatus`

| Значение | Подпись в UI | Смысл |
|---|---|---|
| `idea` | Идея | Есть только замысел |
| `planning` | Планирование | Собирается команда, проектируется |
| `in_progress` | В разработке | Активная работа |
| `paused` | На паузе | Временно заморожен |
| `done` | Завершён | Достигнут результат |
| `archived` | В архиве | Не развивается; только чтение |

Переходы свободные между любыми статусами, кроме правила: проект в `archived`
можно редактировать только после смены статуса (разархивации). Каждая смена
пишется в `project_status_events`. Новый проект создаётся в статусе `idea`.

### 4.2. Видимость проекта — `ProjectVisibility`

| Значение | Кто видит |
|---|---|
| `public` | Все, включая анонимов |
| `authenticated` | Любой вошедший пользователь |
| `private` | Только участники проекта с любой ролью, включая `viewer` (и админы платформы) |

По умолчанию — `private` (черновик никто не увидит случайно). Для тех, кому
проект недоступен, API отвечает `404`, а не `403`, чтобы не раскрывать факт
существования.

### 4.3. Роли участников — `ProjectRole`

| Право | owner | maintainer | contributor | viewer |
|---|:-:|:-:|:-:|:-:|
| Просмотр (в т.ч. `private`-проекта) | ✓ | ✓ | ✓ | ✓ |
| Редактировать README, описание, логотип | ✓ | ✓ | ✓ | |
| Управлять ссылками | ✓ | ✓ | ✓ | |
| Менять статус | ✓ | ✓ | | |
| Менять видимость, название, slug | ✓ | ✓ | | |
| Приглашать / исключать участников ниже своей роли | ✓ | ✓ | | |
| Менять роли (кроме `owner`) | ✓ | | | |
| Передать владение | ✓ | | | |
| Удалить проект | ✓ | | | |
| Менять свою подпись `title` | ✓ | ✓ | ✓ | ✓ |
| Выйти из проекта | — | ✓ | ✓ | ✓ |

Кроме роли у участника есть свободная подпись `title` (до 80 символов), например
«Backend-разработчик» или «Дизайнер» — она показывается в профиле и в списке
команды. Админ платформы (`UserRole.ADMIN`) имеет права `owner` для модерации.

Инварианты:

- у проекта ровно один `owner`; владелец не может выйти, не передав владение;
- передача владения: новый владелец — существующий участник, прежний становится `maintainer`;
- при деактивации пользователя его участие сохраняется, но в публичных выдачах
  он скрывается; если это был `owner` проекта — проект остаётся, владение может
  передать админ.

### 4.4. Ссылки — `ProjectLinkKind`

`repository`, `demo`, `docs`, `design`, `video`, `presentation`, `other`.

Ограничения: только `http`/`https`, длина URL до 2048, подпись до 120 символов,
до 20 ссылок на проект, порядок задаётся полем `position`. Для `repository`
UI показывает иконку по хосту (github.com, gitlab.com, прочее).

## 5. Данные

Все таблицы наследуют `UUIDPrimaryKey` (кроме связочных) и получают аудит-поля из
`Base` (`created_at`, `updated_at`, `created_by`, `updated_by`).

### `projects`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | uuid | PK |
| `slug` | varchar(80) | unique, `^[a-z0-9]+(-[a-z0-9]+)*$` |
| `title` | varchar(120) | not null |
| `summary` | varchar(280) | null |
| `readme_md` | text | ≤ 100 000 символов, по умолчанию `''` |
| `status` | `ProjectStatus` | not null, default `idea` |
| `visibility` | `ProjectVisibility` | not null, default `private` |
| `logo_asset_id` | uuid → `assets.id` | null, `ON DELETE SET NULL`, только изображение |
| `status_changed_at` | timestamptz | not null |

`slug` генерируется из названия (транслитерация) с суффиксом при коллизии, может
быть изменён; старые slug не редиректят (вне объёма).

### `project_members`

| Поле | Тип | Ограничения |
|---|---|---|
| `project_id` | uuid → `projects.id` | PK, `ON DELETE CASCADE` |
| `user_id` | uuid → `users.id` | PK, `ON DELETE CASCADE` |
| `role` | `ProjectRole` | not null |
| `title` | varchar(80) | null |
| `show_in_profile` | bool | default true |
| `profile_position` | smallint | порядок в блоке «Проекты» профиля |
| `joined_at` | timestamptz | not null |

Частичный уникальный индекс: `(project_id) WHERE role = 'owner'`.

### `project_invites`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | uuid | PK |
| `project_id` | uuid → `projects.id` | `ON DELETE CASCADE` |
| `invitee_id` | uuid → `users.id` | `ON DELETE CASCADE` |
| `inviter_id` | uuid → `users.id` | `ON DELETE SET NULL` |
| `role` | `ProjectRole` | не `owner` |
| `title` | varchar(80) | null |
| `status` | `ProjectInviteStatus` | `pending`/`accepted`/`declined`/`revoked`/`expired` |
| `expires_at` | timestamptz | создание + 14 дней |
| `responded_at` | timestamptz | null |

Частичный уникальный индекс: `(project_id, invitee_id) WHERE status = 'pending'`.
Просроченные приглашения переводятся в `expired` лениво при чтении.

### `project_links`

`id`, `project_id` (cascade), `kind`, `url`, `label`, `position`.

### `project_status_events`

`id`, `project_id` (cascade), `from_status` (null для создания), `to_status`,
`actor_id` (→ users, set null), `created_at`.

### `user_profile_blocks`

Порядок и видимость блоков профиля — обычная таблица, одна строка на блок.

| Поле | Тип | Ограничения |
|---|---|---|
| `user_id` | uuid → `users.id` | PK, `ON DELETE CASCADE` |
| `block` | `ProfileBlock` | PK; `about`/`projects`/`stats`/`courses`/`resume` |
| `position` | smallint | not null, `>= 0` |
| `is_visible` | bool | not null, default true |

Уникальность `(user_id, position)` — `DEFERRABLE INITIALLY DEFERRED`, чтобы
перестановка блоков проходила одной транзакцией без конфликтов.

Порядок по умолчанию задаётся в коде (`DEFAULT_PROFILE_LAYOUT`):
`about`, `projects`, `stats`, `courses`, `resume`. Строк в таблице нет, пока
пользователь не сохранил свою раскладку, — тогда используется порядок по
умолчанию. При чтении блоки, для которых у пользователя нет строки (появившиеся
в будущих версиях), добавляются в конец с `is_visible = true`, так что новые
блоки не требуют миграции данных.

Сохранение (`PUT /me/profile-layout`) в одной транзакции удаляет строки
пользователя и вставляет новые. Валидация: каждый блок ровно один раз,
неизвестные блоки отклоняются.

## 6. API

Префикс `/api/v1`. Схемы — в `api/schemas/projects.py`, роутер —
`api/v1/projects.py`, логика — `services/projects.py` (порты репозиториев по
образцу существующих сервисов). Ошибки — существующие `NotFoundError`,
`ForbiddenError`, `ConflictError`, `InvalidUpdateError`.

### Проекты

| Метод и путь | Доступ | Описание |
|---|---|---|
| `GET /projects` | `OptionalUser` | Каталог видимых проектов с поиском и фильтрами (см. ниже) → `PageOut[ProjectCardOut]` |
| `GET /me/projects` | `CurrentUser` | Мои проекты (все роли), включая `private` |
| `POST /projects` | `CurrentUser` | Создать: `title`, `summary?`, `visibility?`; автор становится `owner` |
| `GET /projects/{slug}` | `OptionalUser` | Полная карточка `ProjectOut` + `my_role` |
| `PATCH /projects/{slug}` | contributor+ / maintainer+ по полю (см. §4.3) | `title`, `slug`, `summary`, `readme_md`, `visibility`, `logo_asset_id` |
| `POST /projects/{slug}/status` | maintainer+ | `{status}` → пишет событие |
| `GET /projects/{slug}/status-events` | как просмотр | История статусов |
| `DELETE /projects/{slug}` | owner | Удаление (каскад) |

`logo_asset_id` проверяется через `resolve_image_asset` (PDF отклоняется).
Загрузка логотипа — существующим `POST /assets`.

Лимита на число проектов у пользователя нет.

#### Каталог: поиск и фильтры

В каталог попадают проекты во всех статусах, включая `idea` и `archived`.
Параметры `GET /projects` (все необязательные, комбинируются через И):

| Параметр | Тип | Смысл |
|---|---|---|
| `q` | str ≤ 200 | Поиск по `title` и `summary` (`ILIKE`, как в поиске пользователей и задач) |
| `status` | `ProjectStatus`, можно несколько | `?status=in_progress&status=done` |
| `link_kind` | `ProjectLinkKind`, можно несколько | Есть хотя бы одна ссылка такого типа, например «с репозиторием» или «с демо» |
| `member` | login | Проекты, где пользователь — участник с `show_in_profile = true` |
| `sort` | `updated` (по умолчанию) / `created` / `status_changed` / `title` | Направление: по дате — новые первыми, по названию — А→Я |
| `limit`, `offset` | int | Как в остальных списках: `limit` 1–50, по умолчанию 24 |

Индексы: `projects (visibility, status)`, `projects (updated_at)`,
`projects (status_changed_at)`, `project_links (project_id, kind)`. Если
`ILIKE` станет узким местом — `pg_trgm`-индекс отдельной задачей.

### Ссылки

| Метод и путь | Доступ |
|---|---|
| `PUT /projects/{slug}/links` | contributor+; заменяет весь список (порядок = порядок массива) |

Один `PUT` вместо CRUD по отдельным ссылкам: список маленький, так проще
сохранять порядок и форма редактирования отправляет его целиком.

### Участники и приглашения

| Метод и путь | Доступ | Описание |
|---|---|---|
| `GET /projects/{slug}/members` | как просмотр | Участники с ролями и `title` |
| `PATCH /projects/{slug}/members/{login}` | owner (роль), maintainer+ (`title`), сам участник (`title`) | `role?`, `title?` |
| `DELETE /projects/{slug}/members/{login}` | maintainer+ для ролей ниже своей; сам участник — выход | |
| `POST /projects/{slug}/transfer` | owner | `{login}` — передача владения |
| `GET /projects/{slug}/invites` | maintainer+ | Активные приглашения |
| `POST /projects/{slug}/invites` | maintainer+ | `{login, role, title?}`; `409`, если уже участник или есть pending |
| `DELETE /projects/{slug}/invites/{id}` | maintainer+ | Отзыв → `revoked` |
| `GET /me/invites` | `CurrentUser` | Входящие pending-приглашения |
| `POST /me/invites/{id}/accept` | приглашённый | Создаёт `project_members` |
| `POST /me/invites/{id}/decline` | приглашённый | |

Приглашение отправляет письмо через существующий `EmailJobOutbox`
(категория `project_invite`, шаблон в `templates/emails/`) со ссылкой на `/me`,
если у пользователя есть email. Внутриплатформенных уведомлений пока нет —
входящие приглашения показываются бейджем в шапке и списком в `/me`.

Rate limit: не более 30 приглашений в час на пользователя (Redis, по образцу
`tutor_quota`).

### Профиль

| Метод и путь | Доступ | Описание |
|---|---|---|
| `GET /users/{login}` | public | В `PublicProfileOut` добавляются `layout` (только видимые блоки, в порядке) и `projects: list[ProjectCardOut]` |
| `GET /me/profile-layout` | `CurrentUser` | Полный layout с флагами `visible` |
| `PUT /me/profile-layout` | `CurrentUser` | Сохранить порядок и видимость блоков |
| `PUT /me/projects/order` | `CurrentUser` | `{items: [{project_id, show_in_profile}]}` — порядок и показ проектов в профиле |

В профиле показываются проекты, где пользователь — участник с
`show_in_profile = true`, **и** которые видны текущему зрителю по правилам
видимости проекта. Скрытые блоки не отдаются в `GET /users/{login}` вовсе —
фильтрация на бэкенде, а не на фронте.

### Схемы ответа (сокращённо)

```text
ProjectCardOut: id, slug, title, summary, status, visibility, logo_url,
                members_count, my_role?, member_title? (для карточки в профиле), updated_at
ProjectOut:     ProjectCardOut + readme_md, links[], members[] (login, name,
                avatar_url, role, title), status_changed_at, created_at
```

## 7. Markdown

- Рендер на фронте через уже подключённый `markdown-it` с `html: false`;
  ссылки открываются с `rel="nofollow noopener noreferrer"` и `target="_blank"`.
- Изображения в README — только по `https`.
- Редактор: textarea с превью (вкладки «Редактор / Превью»), как в редакторе
  уроков; переиспользовать общий компонент рендера Markdown, если он есть,
  иначе вынести его в `components/ui`.
- Лимит 100 000 символов проверяется и на фронте, и в схеме.

## 8. Фронтенд

### Маршруты

| Путь | View | Доступ |
|---|---|---|
| `/projects` | `ProjectsView` — каталог и вкладка «Мои» | все / мои — авторизованные |
| `/projects/new` | `ProjectCreateView` | авторизованные |
| `/projects/:slug` | `ProjectView` — README, ссылки, команда, статус | по видимости |
| `/projects/:slug/settings` | `ProjectSettingsView` — основное, ссылки, участники, опасная зона | contributor+ (недоступные по роли поля и вкладки скрыты, см. §4.3) |

### Каталог

- Поле поиска с debounce 300 мс.
- Фильтры: чипы статусов (мультивыбор, с цветом статуса), чипы «Есть репозиторий»,
  «Есть демо» и т.д. по `link_kind`, выбор сортировки; кнопка «Сбросить».
- Всё состояние фильтров синхронизируется с query-строкой URL — ссылку на
  отфильтрованный каталог можно отправить, «назад» в браузере работает.
- Пагинация «Показать ещё»; пустое состояние различает «проектов нет» и
  «ничего не найдено по фильтрам».
- Вкладка «Мои» (`/me/projects`) — те же поиск и фильтр по статусу на клиенте,
  плюс фильтр по моей роли.

### Страница проекта

- Шапка: логотип, название, краткое описание, бейдж статуса, бейдж видимости
  (для участников), кнопка «Настройки» для contributor+.
- Смена статуса — выпадающий список прямо в шапке для maintainer+.
- Основная колонка — README; боковая — ссылки и команда (аватар, имя, `title`,
  роль), история статусов свёрнута.
- Пустой README у участника: призыв «Расскажите о проекте» с переходом в редактор.

### Настройки проекта

Вкладки: «Основное» (название, slug, описание, логотип, видимость), «README»,
«Ссылки» (список с выбором типа и сортировкой), «Участники» (список, смена ролей,
исключение, приглашение по логину с автодополнением из `GET /users?q=`,
pending-приглашения с отзывом), «Опасная зона» (передача владения, удаление с
подтверждением вводом slug).

### Профиль

- `PublicProfileView` рендерит блоки строго в порядке `layout` из ответа.
  Существующее содержимое `ProfileSummary` разбивается на компоненты блоков
  `about`, `stats`, `courses`, `resume`; добавляется `ProfileProjectsBlock`
  (сетка карточек с логотипом, статусом и `member_title`).
- В `/me` — раздел «Публичный профиль»:
  - список блоков с переключателем видимости и перетаскиванием (нативный
    HTML5 DnD) плюс кнопки «вверх/вниз» для клавиатуры;
  - список своих проектов с переключателем «показывать в профиле» и сортировкой;
  - ссылка «Посмотреть как видят другие» на `/people/:login`.
- Входящие приглашения — карточки в `/me` с кнопками «Принять / Отклонить»,
  счётчик в шапке.

### Данные

Zod-схемы в `api/schemas/projects.ts`, клиент в `api/`, логика страниц в
`features/projects/composables` по образцу существующих фич.

## 9. Безопасность и приватность

- Проверка доступа только в сервисном слое; один хелпер
  `ensure_can(project, user, action)` с матрицей из §4.3.
- Скрытые проекты → `404` во всех эндпоинтах, включая участников и ссылки.
- В выдачах участников — только публичные поля (`PublicUserOut`), без email и
  номера студенческого.
- Неактивные пользователи не показываются в списках команды для не-участников.
- Каталог `GET /projects` не показывает `private`-проекты даже их участникам —
  для этого есть `/me/projects`.
- Приглашение нельзя отправить неактивному пользователю и самому себе.
- Преподаватели (`UserRole.TEACHER`) не получают особого доступа: `private`-проекты
  студентов им не видны, если они не участники.

## 10. Миграция

Одна Alembic-ревизия: новые enum-типы, таблицы из §5,
в том числе `user_profile_blocks`; таблица `users` не меняется. Обратная миграция удаляет всё созданное.
Существующие профили получают раскладку по умолчанию без вставки строк — блок «Проекты» пустой и не
рендерится, пока проектов нет.

## 11. Тестирование

Бэкенд (pytest, по образцу `tests/`):

- матрица прав: каждое действие × каждая роль × не-участник × аноним × админ;
- видимость: `404` для каждого уровня, корректная фильтрация в каталоге и профиле;
- каталог: каждый фильтр по отдельности и в комбинации, мультизначения `status` и
  `link_kind`, все варианты `sort`, поиск по `q` без учёта регистра;
- инварианты владельца: единственность, запрет выхода, передача владения;
- приглашения: дубликаты, просрочка, повторное приглашение после `declined`,
  принятие чужого приглашения → `404`;
- статусы: история событий, запрет редактирования в `archived`;
- ссылки: схема URL, лимит, порядок;
- раскладка профиля: валидация дубликатов и неизвестных блоков, дополнение новыми
  блоками при чтении;
- логотип: PDF отклоняется.

Фронтенд (vitest): Zod-схемы, рендер профиля по `layout`, композаблы
настроек; безопасность рендера Markdown (HTML не исполняется).

Перед push — `make check` в `backend` и `frontend`.

## 12. Этапы

1. **Бэкенд-ядро:** модели, миграция, CRUD проекта, статусы, видимость, ссылки, тесты.
2. **Команда:** участники, роли, приглашения, письма, тесты прав.
3. **Фронт проекта:** каталог, создание, страница, настройки.
4. **Профиль:** `user_profile_blocks`, блок «Проекты», раздел настройки в `/me`, приглашения в `/me`.

Каждый этап — отдельный MR, мёржится с зелёным `make check`.

## 13. Принятые решения

| Вопрос | Решение |
|---|---|
| Нужна ли роль `viewer`? | Да: видит проект, ничего не меняет |
| Нужна ли роль `contributor`? | Да, права по матрице §4.3 |
| Лимит на число проектов у пользователя | Нет |
| Какие статусы показывать в каталоге | Все, с поиском и фильтрами (§6) |
| Модерация (скрытие) публичных проектов админами | Не в первой версии |
| Видят ли преподаватели `private`-проекты студентов | Нет |
